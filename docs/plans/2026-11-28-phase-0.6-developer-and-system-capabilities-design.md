# Phase 0.6 design — Developer and system capabilities

**Date:** 2026-11-28
**Status:** Approved by project owner (2026-11-28)
**Starts:** after Phase 0.5 release engineering is complete
**Owner boundary:** iOS/Mac verification belongs to Ammar, not this phase.

## Rationale

The owner selected all four candidate themes for the next roadmap phase and
asked for a standing quality/docs agent. Phase 0.6 is therefore structured as
four sub-phases with separate evidence gates rather than one monolithic change.
Each sub-phase gets an isolated worktree, local commits, and no merge without
explicit approval.

## 0.6.1 — Node-only standalone component harness

**Problem:** `packages/testing` currently offers a fake backend and a
conformance suite for fixtures/protocol, but not a way to mount a standalone
Angular component and assert emitted native mutations without an emulator or
browser.

**Deliverables:**
- A runner in `packages/testing/src/` that boots a component through
  `@angnative/core` + `ReferenceEngine` under Vitest.
- 3–5 component fixtures covering text/prop mutation, child insertion, event
  dispatch and teardown.
- A public API exported from `packages/testing/src/index.ts`.
- At least one negative test that fails when an unexpected mutation is emitted.

**Gate:** `pnpm test` green with the new spec files; no emulator, WebView or
QuickJS runtime required for this harness.

## 0.6.2 — Durable storage backend

**Problem:** `crates/angnative-services-core/src/sync.rs:88-95` uses an
in-memory `BTreeMap` queue while surrounding docs call it durable.

**Deliverables:**
- A pluggable backend trait with an SQLite/KV implementation behind it.
- Restart/reopen round-trip and crash-safe queue tests in
  `crates/angnative-services-core/tests/services_spec.rs`.
- Existing conformance tests preserved unchanged.

**Non-goals:** no encryption claim (`crypto.rs` stays API-shape only), no cloud
sync, no schema migration beyond the initial version.

**Gate:** `cargo test -p angnative-services-core` green, including new
persistence tests; no claim of durability across unsupported filesystems.

## 0.6.3 — Hardware capability plugins

**Problem:** `capability.rs` has declarations/registry/resolver and
`capability-degradation.json` fixture, but the listed hardware capabilities are
data-only; Android `HostCapabilities.kt` is an async fetch/timer host-task
bridge, not a camera/geolocation-style plugin surface.

**Deliverables:**
- Capability tokens and resolver entries for Camera, Biometrics, Geolocation
  and Push Notifications.
- Graceful-degradation tests through the existing fixture path.
- A documented contract boundary: Rust/TS layer only unless a device-backed
  implementation is actually verified.

**Non-goals:** no real camera/biometric/push device API claim without device
evidence; no iOS implementation (Ammar's scope).

**Gate:** Rust + JS tests for declaration/resolution/degradation; evidence doc
states exactly what is verified and what remains a contract stub.

## 0.6.4 — Standing quality/docs agent

A dedicated subagent session is established for this phase and reused after
each sub-phase. It:

- reviews each diff for architecture drift and scope violations;
- fixes known nits: `MAGIC.len()` instead of hardcoded `9` in `bytecode.rs`,
  exact package-specifier matching in `check-web-size-budget.mjs`, the
  misleading `ease`/smoothstep alias in `animation.ts`, and one-shot `finished`
  replay semantics versus WAAPI;
- syncs `STATUS.md`, `README.md`, `docs/SHOWCASE-TRACKER.md`,
  `docs/architecture/issue-register.md` and release notes to fresh evidence.

In this harness the agent is an on-demand session invoked after each phase,
not a continuously running daemon. That limitation is recorded here rather
than papered over.

## Sequencing and gates

1. 0.6.1 → 0.6.2 → 0.6.3, with 0.6.4 invoked after each.
2. Evidence-first: exact commands and observed outputs in a dedicated evidence
   doc before any tracker/status claim.
3. Every sub-phase keeps changes local until reviewed; no push/merge without
   the owner's explicit go-ahead.
